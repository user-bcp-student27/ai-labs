# HU-01 — Completar el manejo seguro de la autenticación por token

## Origen

- **H-AUTH-05 — CORS amplio y configuración de despliegue pendiente.** Evidencia: `auth/src/main/resources/application.properties:4-5,9-11`. La ruta de la clave de firma se externaliza, pero no se ha proporcionado su configuración de despliegue ni la allowlist de producción.
- **H-AUTH-08 — Cuentas demo pueden persistir en bases existentes.** Evidencia: `auth/src/main/java/com/bcp/workshop/auth/LegacyDatabase.java:32-41,58-68,86-101`; `auth/src/main/java/com/bcp/workshop/auth/AuthService.java:20-22`; `auth/src/main/resources/application.properties:13`; `README.md:44`. El hallazgo señala que las cuentas demo preexistentes podrían seguir autenticándose y obtener tokens.

## Contexto

H-AUTH-03 está marcado como Resuelto: el emisor actual genera JWT RS256 con claims `sub`, `role` y `exp`. Esta HU se limita a las filas Pendiente relacionadas con el acceso y la configuración del flujo de autenticación por token.

La matriz indica que no se debe modificar una cuenta persistida hasta acordar cómo distinguir cuentas demo de cuentas legítimas. Tampoco se ha proporcionado una allowlist CORS para producción. La HU no presupone esos datos ni autoriza cambios destructivos.

## Ajustes necesarios

- **H-AUTH-05:** verificar la configuración de la clave externa en los perfiles de despliegue con valores de prueba efímeros. No guardar claves en el repositorio. Obtener y configurar la allowlist CORS aprobada antes de restringir orígenes; no inventar dominios.
- **H-AUTH-08:** acordar una regla segura para identificar cuentas demo ya persistidas. Una vez aprobada, impedir que las cuentas identificadas como demo obtengan tokens y preservar el acceso de cuentas legítimas. No borrar ni desactivar registros antes de esa decisión.

## Criterios de aceptación

1. Con una clave RSA efímera provista por la configuración de prueba, una prueba verifica que el JWT emitido tiene una firma RS256 válida y que sus claims de identidad, rol y expiración corresponden al usuario autenticado.
2. Una prueba de configuración verifica que, si falta la ubicación de la clave o esta no es válida, el servicio no emite un token.
3. En una base de prueba que contenga una cuenta demo preexistente identificada con la regla acordada, la prueba de login comprueba que no se emite token para esa cuenta; una cuenta legítima de control conserva el login exitoso.
4. Después de acordar la allowlist, las pruebas de preflight verifican que un origen incluido está permitido y que uno no incluido no recibe autorización CORS.

## Evidencia esperada

- Resultados de las pruebas de firma, claims y configuración, sin incluir claves privadas ni tokens.
- Resultado de las pruebas con una cuenta demo identificada y una cuenta legítima de control; usar una base aislada y no adjuntar contraseñas.
- Decisión aprobada sobre cómo identificar las cuentas demo persistidas y evidencia de que no se afectó a usuarios legítimos.
- Allowlist de producción aprobada y resultados de pruebas de preflight CORS.
- Actualización de H-AUTH-05 y H-AUTH-08 en `HALLAZGOS.md`, respaldada por resultados reales de pruebas.
